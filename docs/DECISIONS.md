# Architectural decisions and unresolved questions

## Accepted for bootstrap
- **A01:** Claude Code is the first UI/runtime. No custom agent or editor.
- **A02:** TypeScript/Node.js with built-in libraries where practical. No hosted services or DB for v0.1.
- **A03:** Project/user-state stored in JSON and Markdown with explicit versions, atomic updates and validation.
- **A04:** Core domain modules separate from `.claude/skills` adapters.
- **A05:** Native questions are never workflow progression events by default.
- **A06:** Pending decisions require explicit validated choices, not inferential acceptance.
- **A07:** Explain mode uses a restricted read-only inspector; broader runtime restrictions are separate.
- **A08:** Start with a small cohort of meaningful competencies and one complete vertical slice.
- **A09:** Use GSD Core for research/reference only; do not depend on/fork it initially.
- **A10:** The handoff repository is the framework source, not a sample learner project.

## Implementation decisions (M0–M2 session, 2026-11-12)
- **D01 Toolchain.** Node 22 or later (`engines.node >=22`; developed on 22.15). TypeScript 7 compiles `src/` and `test/` to `dist/` with `tsc`, and `node --test` runs the compiled tests. The only dependencies are the dev dependencies `typescript` and `@types/node`. Type stripping in Node 22.15 is still experimental, so it was not used.
- **D02 Three state documents.** `state.json` (workflow), `threads/INDEX.json` (learning threads) and `learner.json` (competency evidence) each carry their own `schemaVersion` and `revision`. Opening a question writes only the threads document, so the workflow file stays byte-identical. Thread transitions receive a frozen workflow snapshot and can only return a threads document. All threads live in one index file for now; per-thread files can come later if the index grows.
- **D03 Write protocol.** Each write takes a cross-process lock (`<file>.lock`, created with `O_EXCL`), re-reads and validates the stored document, compares `expectedRevision` if one was supplied, runs the pure transition, validates the result and replaces the file atomically (temp file in the same directory, fsync, rename, directory fsync). A mismatched revision raises `REVISION_CONFLICT`. Without `expectedRevision` the update is a serialised read-modify-write, which prevents lost updates but does not detect that a human saw an older state. Commands that act on something the learner was shown, such as `decision resolve`, should pass `--expected-revision`.
- **D04 Interrupted writes and stale locks.** A crash before the rename leaves the old file intact and a stray `.*.tmp` file that is never read; the next writer of that document deletes it once it holds the lock. A lock is reclaimed when its owning process on the same host has exited or it is older than 30 seconds. Reclaiming happens under a second `O_EXCL` marker (`<file>.lock.reclaim`) with staleness re-checked while it is held, so two waiters cannot both delete the lock. A marker older than 5 seconds is treated as left by a crashed reclaimer. One window remains: a live process that holds a lock for more than 30 seconds can have it taken away.
- **D05 Event log.** `events.jsonl` is appended after the state file is replaced, while the lock is still held. If the process dies between the two steps, the state is committed and the event is missing. Question events store thread ids and message refs, never question text.
- **D06 Schema changes from the spec fixtures.** `ProjectState` gains `checkpoints` (typed `decision_gate`, `understanding_gate` or `learning_opportunity`, each with `blocking` and `status`). `pendingCheckpointIds` was dropped because it can be derived (`evaluateTaskGates`), and storing it would allow the two to disagree. Tasks gain `acceptanceCriteria`, `verifications`, `startedBy` and an `executing` status. Threads gain `suspended` status, `pausedStatus` and short `entries` in place of bare `messageRefs`. The fixtures in `specs/` were updated to match, and a test validates them.
- **D07 Gates.** `decision_gate` checkpoints are always blocking and are satisfied only by resolving their decision. `learning_opportunity` checkpoints are never blocking. A pending optional checkpoint does not block a start; the `task_started` event lists it, and `checkpoint defer` records an explicit deferral with a reason. Task dependencies must already exist when a task is added, which makes cycles impossible without a graph search.
- **D08 Verification.** A task completes only when every acceptance criterion has a `pass` result with a non-empty evidence reference. A run with failures is recorded and the task stays `executing`. The schema rejects a `complete` task with no accepted verification, so a hand-edited file cannot claim completion either. The framework cannot check that an evidence reference points at a real test run; that remains the job of the skill and the reviewer.
- **D09 Routing.** Without a classifier, free text is always a non-mutating question. Only `/learn-build` maps to a mutating operation. If a classifier labels free text as a decision or implementation request, the route is downgraded to `unclear` with `confirmationNeededFor` set. Decisions are recorded only through `decision resolve` with an exact option id and a confirmation ref. The skill layer is responsible for turning "let's use sessions" into that call after confirming with the learner.
- **D10 Proficiency is derived.** `learner.json` stores evidence only; levels are computed from it so they cannot drift. Each evidence type caps the level it supports (`introduced` 0, `explained` 1, `predicted` and `modified` 2, `debugged` and `transferred` 3). Learner self-assessment counts as 0 and low-confidence evidence is capped at 1. Contradicting evidence lowers the level. Competency ids are the plain slugs from `docs/LEARNING.md`.
- **D11 Framework-root guard.** `init` refuses a directory whose `package.json` is named `learnbuild`, so tests and manual runs cannot create `.learn-build/` in the framework source. `--allow-framework-root` overrides this.
- **D12 Prose standard loading.** `src/prose/standard.ts` reads `standards/PROSE_STYLE.md` and `withProseStandard()` embeds the full text in an instruction string. `learnbuild install` runs every skill and agent template through it, so each installed instruction file carries the complete standard and the templates carry no copy. A test checks every rendered file contains the standard verbatim, exactly once (T20).
- **D13 Explain inspector.** `src/explain/inspector.ts` is the read-only capability. It imports only `lstat`, `open`, `readdir`, `realpath` and `stat` from `node:fs/promises`, opens files with flag `r`, and spawns no process; a test checks the import list. Every path is resolved with `realpath` and must stay inside the resolved root. Secret files (`.env*` except templates, key and certificate files, credential files), VCS data, vendor directories and build output are refused when named and skipped in scans. Symlinks are never followed during a scan: links that leave the root are reported as skipped, and links inside the root are skipped because their target is scanned at its real path. A path check followed by an open is not atomic, so a process that rewrites the repository during inspection could defeat it; the inspector assumes the repository is not being modified concurrently by an attacker.
- **D14 Bounded scans report coverage.** Limits apply to bytes per file, files per walk, depth, total bytes per search, snippet lines and result count. Every scan returns a `coverage` object with `truncated`, the limits that were hit and the paths skipped with reasons. `found: false` therefore means "not found in what was covered", and callers must read `coverage.truncated` before saying something does not exist.
- **D15 Changed-code inspection deferred.** `/learn-explain --changed` needs Git. `git diff` against a working tree can run clean filters, textconv and external diff commands defined in the inspected repository's own `.git/config`, and can rewrite the index. Hardening flags exist for most of these, but that path has not been tested against a hostile repository, so no Git command is run yet.
- **D16 Symbol lookup is textual.** `findSymbol` matches declaration keywords and common assignment forms with a regular expression. It has no parser, so it can miss unusual declarations and cannot tell scopes apart. Results are candidate declaration lines with exact `path:line` citations.
- **D17 Skills are templates, installed per project.** Skill and agent sources live in `templates/claude/`, outside this repository's own `.claude/`, so they are not active while developing the framework. `learnbuild install --root <project>` copies them into the learner project's `.claude/`, refuses to replace a file that differs unless `--force` is given, and merges one hook into `.claude/settings.json` while keeping its other content. The skills call `learnbuild` by name, so it must be on `PATH` (for example through `npm link`).
- **D18 Explain mode enforcement, as tested.** `/learn-explain` forks into the `learn-explainer` subagent, whose only tool is Bash. A `PreToolUse` hook (`learnbuild hook explain-guard`) inspects each call: for `agent_type: learn-explainer` it approves a command only if it tokenises to exactly `learnbuild explain <subcommand>` with known options, and blocks everything else with exit 2. Unquoted shell metacharacters, expansions inside double quotes, chaining, redirection and `--root` are rejected. Calls from the main session and other agents pass through with no opinion. The hook command blocks if `learnbuild` is missing or crashes, which also blocks every tool call in that project until it is fixed.
  Tested in headless Claude Code 2.1.322 on 2026-11-12: inspector commands ran without a permission prompt; `cat .env`, `echo hi > NOTES.md` and `learnbuild explain overview; touch PWNED` were each blocked; the fixture tree was byte-identical afterwards and the `.env` value never appeared in the transcript.
  Two things did not work and shaped this design. Hooks declared in the agent's frontmatter or in the skill's frontmatter never ran for the forked skill, so the hook is registered in project settings. Without the hook's explicit `allow`, every inspector command in the subagent waited for approval.
  Limits: enforcement depends on Claude Code sending `agent_type` in the hook payload and on the project's settings hook being active. A user who removes the hook, or a Claude Code version that changes either behaviour, leaves only the normal permission prompts. Re-run the live test after upgrading Claude Code.
- **D19 Decisions need an explicit command.** `/learn-decide <option>` is the only skill that pre-approves `learnbuild decision resolve`, and it sets `disable-model-invocation: true`, so the model cannot start it from its own reading of a message. The skill requires the argument to equal an option id and passes `--expected-revision`. `/learn-ask`, `/learn-resume`, `/learn-progress` and `/learn-decide` set `disallowed-tools: Write, Edit, NotebookEdit`. D22 and D23 add hook enforcement on top of this.
- **D20 Free-text questions.** Claude Code has no documented way to force a skill onto every message. In testing, an unprefixed question sometimes invoked `/learn-ask` and sometimes was answered directly. D24 makes the outcome the same in both cases.
- **D21 Starting from zero.** `learnbuild new` is the entry point for someone who has never programmed. It asks for a name, turns it into a folder name, creates the folder, runs `git init` if Git is present, initialises state, installs the skills, agent, hooks and a project `CLAUDE.md`, and opens Claude Code in the folder with `/learn-new` as the first message. It prints plain text, unlike every other command. It refuses to nest inside another project or overwrite a folder that has files. It also installs the `/learn-new` skill under `~/.claude/skills/`, which is the only thing LearnBuild writes outside the project; that lets `/learn-new` work in any session. A session started elsewhere cannot load the new project's skills and hooks, so in that case `/learn-new` creates the folder and tells the learner the two commands to reopen Claude Code inside it.
- **D22 Edits need a started task.** The project `PreToolUse` hook blocks `Write`, `Edit`, `MultiEdit` and `NotebookEdit` on project files unless the workflow status is `executing`, which only `learnbuild task start` sets. Markdown notes under `.learn-build/` and draft plans in `.learn-build/plans/` are always writable. The JSON state files are never writable through those tools. Files outside the project are not the hook's concern.
- **D23 Shell writes are caught by a heuristic.** While no task is executing, the same hook blocks Bash commands that look like file writes: redirection, heredocs, in-place edits, package installs, file-moving commands and Git commands that change the tree. This exists because a live run showed the model writing notes with `cat > file` instead of the Write tool. It stops ordinary drift. It is pattern matching, so a command constructed to hide a write would pass, and it must not be described as a security boundary. Only explain mode has a strict allow-list.
- **D24 State and rules on every message.** A `UserPromptSubmit` hook prints the project status, any pending decision and the rules for free text into the model's context for each learner message, so they do not depend on chat history or on a skill being chosen. While a decision is pending, the hook also records the message on a question thread itself. T01–T03 therefore hold even when the model answers without invoking `/learn-ask`, which is what happened in a live run. The hook writes only the threads document and fails silently, since it adds context and enforces nothing.
- **D25 Plans are applied whole.** `/learn-plan` writes `.learn-build/plans/plan-NN.json` and runs `learnbuild plan apply`, which adds every task, decision and checkpoint in one revision or none. Each task must have at least one acceptance criterion. `learnbuild next` computes the single next step (`plan`, `request_decision`, `await_decision`, `await_evidence`, `start_task`, `continue_task`, `done` or `blocked`) and `/learn-build` acts on it.
- **D26 Building needs the learner's command.** `/learn-build` sets `disable-model-invocation: true` and is the only skill that pre-approves `learnbuild task start`. "Just build it" in free text gets a reply naming the command. This costs a novice one extra command per step and was kept because it is the framework's central promise.
- **D27 Pre-approval lasts one turn.** A skill's `allowed-tools` apply only to the turn in which it was invoked. A skill that asks a question and acts on the answer in the next turn will trigger a permission prompt for that action. `/learn-new` avoids this by naming the project from the idea when it can.
- **D28 Git is asked about, never assumed.** A new project gets a repository only if the learner says yes. `learnbuild new` asks "Do you want to initialise a Git repository for this project?" with `y`, `n` or `?`; `?` explains what Git is, when it is worth having and links the Pro Git book. `--git` and `--no-git` answer it up front. When the question cannot be asked in a terminal, as when `/learn-new` creates the project from inside a session, the choice is left open and `/learn-new` asks it in conversation before the brief, answers follow-up questions, then runs `learnbuild git --init` or `--skip`. The answer is stored as a `Version control:` line in `.learn-build/PROJECT.md`, so it is asked once. The guidance given is that commits are worth it for history to go back to, for sharing, or for a copy kept elsewhere, and that skipping is reasonable. Nothing creates a remote, pushes or recommends a hosting service unless the learner asks; `/learn-build` commits only when a repository exists. `learnbuild new` no longer runs `git init` on its own.
- **D29 The first three commits are explained and agreed before they happen.** Saying yes to Git means `/learn-build` commits each verified step. In a live run, an instruction to announce commits beforehand was ignored, so this is enforced by the hooks. A `git commit` in a repository with fewer than three commits is blocked, and the block message lists what to tell the learner. The first covers what a commit is, why now, which files, the two commands and what each does, that nothing is uploaded, and how to see it afterwards. The second covers why, which files changed and the commands. The third is a few sentences and says later commits will happen without asking. The learner's next message marks that commit number acknowledged and the same command then passes; agreement to one commit does not carry to the next. A learner who declines gets no commit. The skill tells the model to attempt the commit first so the pause is always registered; when it explained first without attempting, the learner's agreement was not counted and an extra round was needed. From the fourth commit on there is no pause and the commit line is reported in the step summary. The marker is `.learn-build/commit-intro.txt`.
- **D30 Natural replies move the project on (replaces the command-only rule in D19 and D26).** Feedback from hands-on testing was that being told to type `/learn-plan` or `/learn-build` for each step was friction. The `UserPromptSubmit` hook now classifies each learner message with fixed rules, no model involved. A short message made only of go-ahead words ("next", "start", "ok let's go") is a go-ahead, and the hook names the skill for the next stage: `learn-new` if the brief is unwritten, `learn-plan` if there is no plan, otherwise `learn-build`. While a decision is pending, a message that is one option's name, alone or after a stock lead-in such as "go with", is a choice. Anything with a question mark or a word outside the small vocabulary is neither. The classification is written to `.learn-build/turn.json`.
  The `PreToolUse` hook enforces it: `learnbuild task start` runs only on a go-ahead turn, and `learnbuild decision resolve` only on a choice turn and only for the option the learner named. This is stricter than before, when the model could run either command on any turn, and it is why `disable-model-invocation` could be dropped from `/learn-build` and `/learn-decide`. "The simple one", "maybe sessions" and "sessions?" are not choices; the reply tells the learner which name to type. The slash commands still work and map to the same two intents.
  Known edge: a bare "yes" or "ok" is a go-ahead even when it answers a question the model just asked. The hook tells the model to treat it as that answer in that case, but the permission to start a step exists for that turn.
- **D31 Presentation.** The project `CLAUDE.md` defines a fixed set of stage banners, asks for tables when comparing options, and marks new terms. `learnbuild next` and `learnbuild progress` return a `display` checklist with a progress bar that skills show as it is. `learnbuild new` and `learnbuild help` use colour when the output is a terminal and `NO_COLOR` is unset. How closely the model follows the layout guidance is not enforced.
- **D32 Choices are shown, not filed away.** `/learn-plan` presents a table of the main choices it made, the reason for each and what else was possible, then invites questions about any row. `ARCHITECTURE.md` is mentioned once as the longer version.
- **D33 Editor and help.** `learnbuild new` looks for a known editor on `PATH` and offers to open the project folder in it; with none found it suggests one. `/learn-help` and `learnbuild help` list what the learner can say and every command; a test keeps the help skill, the terminal help and the README in step with one list in `src/cli/guide.ts`.
- **D34 The learner ends up inside the project folder.** A program cannot change the working directory of the shell that launched it. After `learnbuild new` (once Claude Code exits, or straight away with `--no-launch`), LearnBuild starts the learner's own shell in the project folder and says that `exit` returns to where they began. It does not nest a second shell for the same project. `learnbuild open <folder>` does the same for an existing project and runs `/learn-new` first if the brief or the Git answer is missing. A Claude Code session cannot move itself into another folder or load that folder's skills and hooks, so `/learn-new` from a session elsewhere still ends with `/exit` followed by `learnbuild open <name>`.
- **D35 Owner decisions, 2026-11-12.** Understanding checks cannot be skipped: a learner who does not know gets another explanation and an easier question on the same idea. A bare "yes" or "ok" counts as a go-ahead, including when it answers a question the model just asked (the edge noted in D30); this is accepted for now.

## Open — decide empirically during implementation
- Read-only tool restrictions for explain mode: resolved for now by D18; re-verify on Claude Code upgrades.
- Whether first natural-language question routing needs a dedicated tool hook or can rely on skill/orchestrator instructions plus explicit mutating commands.
- Target-project installation: resolved by D17 and D21. Publishing the package so that `npm install -g learnbuild` works is the owner's call and has not been done; until then `npm link` is required.
- Whether learning thread transcripts stay in chat or a locally redacted message store; default to minimal metadata.
- Whether to add an SQLite event store later if JSON concurrency becomes painful.
- First supported sample stack for demonstration: prefer a small TypeScript client/API with simple persistence; avoid requiring external cloud accounts.

Do not expand any open decision into infrastructure work unless v0.1 acceptance demands it.

## Prose standard (confirmed)
The project owner's prose rules are maintained verbatim in `standards/PROSE_STYLE.md`. Development agents must follow them through `CLAUDE.md`; runtime agents must receive the complete canonical content through shared prompt assembly, including isolated contexts. Representative prose review and prompt-assembly contract tests are required (T19–T21).
